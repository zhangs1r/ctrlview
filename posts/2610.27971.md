## 它想干什么

装配单元的输送线停着等料。规划器决定重启它，决策那一刻它读到的是线在跑、夹爪开着。推理要一秒上下，命令还得等操作员点头。这一秒里有人把线置成暂停，去清卡料。

命令最后到达单元控制器，格式合规，参数合规，唯一失效的是它假设的那个现场。线转起来了。论文在讨论里点到这条后果，一条发在刚被按停的线上的重启命令，可能让机械臂朝按暂停的那个人移动。

作者给这段落差起了个名字，执行间隔，指的是一个动作在被提出时是允许的，在被放行时已经不允许。它不是延迟问题。延迟只是把窗口拉长，能不能拦住取决于两件更具体的事，最后一道检查落在哪个串行化域上，比的是哪一份状态的哪个版本。

==命令的格式和参数都没错，错的是它假设的那个现场==。工业单元里现场没有单一的主人。单元控制器拥有 line.state 和它自己的版本，store 里那份只是滞后的副本，MES 手里还有配方。每个组件按自己的顺序、自己的钟提交更新，检查放在哪一层，就只能看见那一层排过序的变化。

作者交了三样东西。AIS 是一份契约，生产者随命令声明决定的有效期与依赖的现场条件。XAIR 是执行这份契约的运行时，放行前重检，或者把授权原子地提交进 store，或者把命令发成版本条件命令，让拥有状态的控制器在产生动作的那一次扫描里比版本。第三样是评测，六个试验台配置加一个 OpenPLC 运行时，地面真值在跑之前就写好。

结果分两半。副本上的检查一律留一段无人看守的区间，分布式试验台上暂停写在提交后 6 到 16 ms 的那批至少一半逃过去，广域节点 160 ms 起，200 ms 时全逃。搬进控制器扫描，分布式试验台 1100 次注入试验里陈旧生效 0 次，但只有版本条件命令同时拦住了暂停被撤销的情况，联锁在那里漏了 **28.5%** 到 **29.7%**。误撤是另一本账，分布式试验台上全局版本在 100 Hz 下撤掉 **64%** 的合法命令，读集版本在连续压力信号上撤掉 **37%**，谓词真值版本零。

**这节要你记住的是，命令没错，错在它到得太晚。**

## 一、问题背景

### 1.1 被控的是什么

被控对象是单元里的一条输送线。line.state 取 RUN 或 PAUSED，操作员或 MES 都能置位，PAUSED 让线停下。夹爪有 gripper.state。RESUME 的物理后果就是线转起来。

单元控制器每 **10 ms** 扫一次程序。这个周期在论文里出现两次，仿真 OPC UA 服务器跑的是 10 ms 扫描，OpenPLC v3 上的 Structured Text 任务也是 10 ms。

XAIR 站的那一层在毫秒到秒之间。上有分钟级的规划与 MES，下有 50 ms 以内的 PLC 联锁。硬实时不归它管，急停与安全级功能仍走安全 PLC 与机器人安全控制器，不经过 XAIR。

**这节要你记住的是，XAIR 只管毫秒到秒这一段，硬实时还在 PLC 里。**

### 1.2 为什么难

难在状态没有单一主人，时间也没有单一读数。

用 C(t) 表示 store 里 t 时刻的上下文快照，X(t) 表示控制器自己那份状态，C 里的对应部分是一份会滞后的副本。所谓串行化域，就是一个组件按自己的顺序处理更新的范围，域内的更新有先后，跨域没有。检查放在 store，看不见还没复制过来的控制器变化。检查放在控制器扫描，看不见 MES 那边的配方变化。==检查放在哪个域，就只能看见那个域排过序的变化==。

时间也是各自量的。检查端手里只有自己的钟和生产者写下的 t_d，测出的已过时间 â 带着时钟偏移，偏移上界记作 ε。要保证真实间隔 a ≤ d，检查端得接受 â ≤ d − ε。这个 ε 检查端验不了，原子提交只能拒掉超前自己时钟超过 ε 的时间戳，这挡住一部分违约，挡不住全部。

第三种失效更隐蔽。暂停在验证之后、放行之前被恢复，谓词在放行那一刻全部为真，命令合规地发出去，可线真的停过，这期间一条要求"必须全程成立"的策略被违反了。论文把这种叫历史违规，形状是 A-B-A。这类检查之后到使用之前状态被改掉的竞争，在系统安全里叫 TOCTOU。

**这节要你记住的是，状态分属几个域，时间也是各自量的。**

### 1.3 前人两条路

一条是形式化那一路，一条是授权与并发控制那一路。下面这张表逐行给出它怎么判、差在哪，闸门指放行前做最后一次检查的那个组件。

| 方法 | 它怎么做 | 差在哪 |
|---|---|---|
| runtime enforcement 与 shields | 从时序规约算出最小干预修正，压制或改写会违规的输出 | 判的是输出轨迹与规约的符合性，有效性不随命令走，也看不见撤销过的变化 |
| ModelPlex 与 command governor | 从验证过的混合系统模型合成监视器，或把连续输入整形进约束集 | 依赖一份被验证过的模型，判的是模型与现场的一致 |
| Simplex 与 SOTER | 检测到不可接受行为就把权限切给验证过的后备控制器 | 决定谁在开车，不判这一条离散命令该不该放行 |
| ROS 2 action 与 ROSRV、ROSMonitoring | 给目标一个生命周期与取消语义，或拦消息按形式属性检查 | 检的是消息轨迹，有效性不随命令走 |
| OPA 1.21（通用策略引擎） | 查询时对副本求值策略，允许或拒绝 | 快，不读 store，也不留放行记录；版本得由别人给 |
| If-Match、CAS、fencing token、Kubernetes 的 resourceVersion、Redis 的 WATCH | 资源拥有者比对客户端读到的版本，不符就拒 | 版本由拥有者自己控制，没有生产者把期望版本写进契约的那一环，也没有截止时间 |
| typed-plan firewall 与契约行为树 | 把规划器输出绑成带类型的意图或能力契约，闸门放在机器人侧 | 契约是静态的，不在放行时刻重检变化的上下文 |
| LLM agent 的 TOCTOU 防御、OpenPort 的状态见证、FBS | 用提示重写、状态完整性监控、检查与使用合一的工具调用，或按安全余量与近期波动估一个批准的有效期 | 检查在 agent 或单个网关里做，按本文的定义算副本上比较 |

表外还有一条线是延迟分析。汽车多速率任务链与 ROS 2 处理链能算出数据到达执行器时有多旧。旧和假设失效是两件事，决策一毫秒后有人按下暂停，数据再新也没用。

作者自己说这些机制没有一个是新的，点名点到的祖谱有 If-Match、CAS、fencing token、使用控制、租约、乐观并发控制、线性化点、只追加日志。他们把贡献落在五个地方，工业单元里多生产者对着控制器拥有的状态；最后一道检查能落在哪些串行化域；全局、读集、谓词真值三种版本作用域的分野；一条让最后一道检查在拥有状态的控制器里跑的版本条件命令；以及一套把陈旧放行、误撤、延迟、落点放在一起测的协议。

**这节要你记住的是，前人各管一段，没人问最后一道检查该落在哪个域。**

### 1.4 这篇的做法

契约加运行时加落点评测。AIS 把前提条件写成合取的比较式，每条只看一个路径，读集于是能从语法直接读出来，store 才有办法在每次更新时顺手维护版本。操作员还能按动作类型强加谓词，生产者删不掉。核心机制一句话，**把最后一道检查搬进拥有这份状态的控制器扫描，比的是动作读过那几个路径的版本**。作者自己把边界说死了，这不构成安全认证，只管假设在放行时是否仍成立。

## 二、总体结构

<figcaption><b>图 4</b>　生产者提交 AIS intent，XAIR 对带版本的快照做验证。网关重检或提交之后才释放，也可以直接发一条版本条件命令给拥有状态的单元控制器。控制器把自己那份状态与版本经 XAIR 的上下文接口写回 store。虚线框是信任域，红点是部署必须认证的入口，原型只保护了策略接口。（原图，取自论文 arXiv 2610.27971）</figcaption>

一条命令的路线是这样。生产者（AI 策略、视觉管线、操作员、MES）提交 AIS intent，也就是一条带有效期与前提条件的动作请求。XAIR 校验 JSON Schema，按动作类型追加操作员强制谓词，对单一快照验证，记下验证时刻的读集版本。网关拿到授权后，在 t_g 重读快照重检，或者请 XAIR 在 t_c 用一次 store 操作把授权提交下来，然后才释放进中间件（ROS 2 或 OPC UA）。另一条出口是把命令直接发给单元控制器，附带期望版本与绝对截止时刻。控制器把自己那份状态和版本经 XAIR 的上下文接口写回 store，这就是 store 里那份副本的来源。

这张表把阶段、章节与输入输出对起来。

| 阶段 | 落在哪一节 | 输入 | 输出 |
|---|---|---|---|
| 提交 | 4.1 | 生产者声明的 w、d、P、S 与载荷 | 一条 AIS intent |
| 验证 t_v | 3.2 与 4.2 | 单一快照 C(t_v) 与操作员策略 | Authorized、Revoke、Expired、Delay、Degrade，附带 ν_R(t_v) |
| 放行检查 | 3.4 与 4.2 | 版本、已过时间、谓词 | Withheld，或 Committed 加一条授权记录 |
| 释放 t_m | 4.2 | 授权记录 | 一次中间件调用 |
| 生效 t_a | 3.4 | 命令携带的期望版本与截止时刻 | 控制器扫描内执行或拒绝 |
| 审计 | 4.2 | 网关与执行器的报告 | 生命周期记录与 actuation log |

生命周期被拆成 Authorized、Committed、Released、Withheld、Effect confirmed、Failed、Unknown effect 几个状态。__授权成功不等于执行成功__，只有执行器或控制器的报告能把它推到 Effect confirmed，没有反馈的停在 Unknown effect。SER 与 FPR 一律从放行决定算，不从验证标签算。

**这节要你记住的是，三处检查共用一个 store，区别在谁读、读哪一份。**

## 三、方法拆解

### 3.1 一条 intent 里装了什么

一条意图写成 $I = (t_d, w, d, P, S, \alpha, r, p)$ 这个八元组。$t_d$ 是决策时刻，$w$ 是新鲜度窗口，$d$ 是可选截止，$P$ 是前置条件，$S$ 是硬约束，$\alpha$ 是动作描述，$r$ 是目标资源，$p$ 是优先级。

$w$ 与 $d$ 分工不同。$w$ 卡的是验证那一刻距决策过了多久，$d$ 卡的是释放那一刻距决策过了多久，没声明 $d$ 时取 $d = w$。所以一条验证时还算新鲜的决定，可能在放行时已经太老，这两道时间门不能合并。

时刻的先后是

$$ t_d < t_v \le t_\ell < t_m \le t_a, \qquad t_\ell = \begin{cases} t_g & \mathrm{optimistic} \\ t_c & \mathrm{atomic} \end{cases} \tag{1} $$

$t_v$ 是验证，$t_\ell$ 是最后一次检查，$t_m$ 是释放进中间件，$t_a$ 是执行器生效。乐观模式下 $t_\ell$ 就是网关那一次重读 $t_g$，原子模式下就是提交 $t_c$。另记 $\Delta_g = t_\ell - t_v$，$\Delta_r = t_m - t_\ell$。gate 永远看不到 $C(t_m)$，因为释放发生在它最后一次读之后，把 $t_g$ 与 $t_m$ 分开写，残余风险才量得出来。

**这节要你记住的是，w 管验证那一刻，d 管释放那一刻。**

### 3.2 什么算可放行

可放行有两套定义，一套给验证，一套给释放。$a(t) = t - t_d$ 是已过时间。

$$ V_v(I) = A_v(I, t_v) \tag{2} $$

$$ V_g(I) = V_v(I) \wedge A(I, t_g) \wedge \nu_R(t_g) = \nu_R(t_v) \tag{3} $$

$A_v$ 要求 $a(t) \le \min(w,d)$、$P(C(t))$、$S(I,C(t))$ 三条同时成立，$A$ 只把时间条件换成 $a(t) \le d$。这两个是地面真值，真实闸门判出来的是 $V_v$ 与 $V_g$。等式里第三项 $\nu_R$ 是读集版本，$R(I)$ 是从谓词语法直接读出来的路径集合，RESUME 的读集就是 line.state 与 gripper.state 两条。

时间门还有一个容易写错的地方。gate 比的是 $d - \varepsilon$，不是 $\min(w,d)$，所以 $V_v$ 成立推不出 $V_g$ 成立。

把账算清楚。一条 intent 带 $|P| + |S|$ 条比较，每条只读一个路径。放行判定要 1 条时间不等式、$|P|$ 条前置条件、$|S|$ 条硬约束，再加 1 条版本等式，一共 $2 + |P| + |S|$ 个条件同时成立。反过来，$|R|$ 条路径的历史被压成 1 个标量 $\nu_R$，所以随命令走的有效性数据量与路径条数无关。至于区间能不能全关掉，每个拥有者只提供 1 个串行化域，要把 $]t_\ell, t_a]$ 全关掉至少要 $k$ 次检查，$k$ 是读集跨了几个拥有者，$k = 1$ 时一次扫描就够。

闸门要比较的那个版本，三件套要说全。初值来自 $t_v$ 那次单一快照的读取，XAIR 把 $\nu_R(t_v)$ 连同判定一起返回。残差是释放时刻的版本等式与时间不等式，驱动闸门开或关。兜底有三层，操作员按动作类型强加的谓词生产者删不掉，谓词语法只接受合取所以每条被读的路径都在读集里，任何一处求值失败一律按拒绝算。

__最后一道检查要落在拥有那份状态的串行化域里，比它读过的那个版本__。

**这节要你记住的是，放行要同时过时间、谓词和一个版本等式。**

### 3.3 三种版本作用域

要判断上下文变过没有，只看谓词现在成立不够，还得有一个版本。论文定义了三种口径。

全局版本每一条被接受的更新都推进，等价于读集包住所有路径的特例。读集版本 $\nu_R(t)$ 只在该路径或它的祖先、后代发生值变化时推进，值变化按 store 里存的原值算，在规范化之前，所以 1 变成 true 也算变过。谓词真值版本 $\pi_I(t)$ 只在某个谓词的注册或真值翻转时推进。

规范化那一步是把存的值映射到字面量的类型，能解析就转换，转不了就让比较失败。版本算在规范化之前，后果是一处表示法的改动也能推进版本，撤掉一条本来合法的 intent，但绝不会把真实变化藏起来。

<figure src="2610.27971-fig2.jpg" caption="同一串更新下哪个版本会推进。">
<figcaption><b>图 2</b>　无关传感器报值、压力从 120 变到 180 但都没越阈。全局版本两次都动了，读集版本只动压力那次，谓词真值版本只在暂停与恢复时动。最右一列是每种闸门在 t_g 那一刻的判定，暂停又被恢复那一列只有带版本的闸门拦得住。（原图，取自论文 arXiv 2610.27971）</figcaption>
</figure>

误撤是版本条件的固有代价，因为它 fail-closed，撤一条合法 intent 在它看来和拦一条过期 intent 没有区别。设 $\lambda$ 是推进该版本的那类更新的速率，更新与提交相互独立，一条合法 intent 被撤的概率是

$$ \Pr[\text{revoke} \mid \text{valid}] = 1 - e^{-\lambda \Delta_g} \quad (\text{Poisson}), \qquad \min(1, \lambda \Delta_g) \quad (\text{periodic}) \tag{4} $$

两种写法在 $\lambda \Delta_g$ 很小时都近似等于 $\lambda \Delta_g$，也就是检查间隔里平均发生几次推进。代价等于作用域放行的更新率乘上闸门延迟。收窄作用域是压 $\lambda$，把闸门挪近一点是压 $\Delta_g$。

三种作用域的形状差别在误撤上最看得清。全局版本会被同一单元里任何一个传感器的新值推进，一条 RESUME 会被无关的更新撤掉。读集版本会死在"值变了但谓词没翻"上，压力从 120 变到 180 仍低于阈值，谓词一直为真，版本还是动了。谓词真值版本在这种情况下不动，代价是每次碰到被读路径的更新都要把注册过的谓词重求一遍。

__版本条件命令只在控制器自己的版本仍等于命令携带的那个版本时才执行__。

**这节要你记住的是，版本管得越宽，误撤越多，挡下的变化也越多。**

### 3.4 最后一道检查放在哪

<figure src="2610.27971-fig1.jpg" caption="验证、两种放行模式与版本条件命令。">
<figcaption><b>图 1</b>　红色竖条是检查看不见的那一段。乐观模式在 t_g 与 t_m 之间，原子模式在 t_c 与 t_m 之间。版本条件命令把比较挪到控制器产生生效的那次扫描里，那一格没有留白。（原图，取自论文 arXiv 2610.27971）</figcaption>
</figure>

第一处是乐观模式。网关在 $t_g$ 重读快照，重检时间、谓词、版本，通过就释放。优点是一次读加上一次比较，代价是 $]t_g, t_m]$ 这一段没人看守。

第二处是原子提交。网关请 XAIR 在 store 的一次操作里比版本、用 store 的钟比时间、拒重复、追加一条授权记录，这一串与所有上下文更新串行。它给出一条严格排序的授权，但不让执行变原子。命令仍然在 $t_c$ 之后才到中间件，$]t_c, t_m]$ 一样存在，论文叫它提交后失效。==原子提交买到的是顺序，不是安全==。每条被提交的授权在提交时都合法，后续更新相对它有确切位置，所以提交后失效事后能从 store 的版本里查出来。这些记录本身还是一份日志，幂等的执行器可以据此把每条命令至多执行一次。

第三处是控制器扫描。这是版本条件命令做的事。网关把控制器那份状态在检查时刻的版本，加上绝对的截止时刻 $t_d + d - \varepsilon$，一起放进命令里。控制器在产生生效的那一次扫描里比自己的版本是否仍等于它，并看时间过没过，两条都成立才执行。评测里的 PLC 程序只比版本，截止时间放在网关兜。

这条命令和 If-Match 长得像，差别在期望版本由谁写。If-Match 的版本是客户端自己读来的，这里是一个从没和控制器说过话的生产者，在契约里写下它依赖的版本。==版本由生产者写进契约，控制器才拒得掉它没看见的状态==。

保证成立要靠五条假设。

- A1 控制器是那份状态的唯一写者
- A2 版本在 $P$ 或 $S$ 读到的变量变化时推进，最好只在它们变化时推进
- A3 store 里的副本把状态和版本一起复制，检查看到的版本属于它评估的那份状态
- A4 只要还有 intent 可能携带某个版本值，这个值就不得复用，跨重启也不行
- A5 检查与生效在同一次扫描里，生效就意味着动作开始

对照物是控制器本地联锁，它也在扫描里判，判的是谓词真值。陈旧生效这一项两者都是零。差别出现在暂停被恢复的场合，联锁看到线在跑就执行，版本却已经动过，版本条件命令拒。

代价这一侧也要说清。联锁不用改控制器接口，扫描里只是多几条比较。版本条件命令要给控制器加一个期望版本入参，存量 PLC 的程序和协议都得改，而且只管得住控制器拥有的那部分状态。评测里一次扫描 1.6 到 5.4 µs 均值，99 分位 15.1 µs，扫描周期 10 ms，比较本身离瓶颈还很远。

**这节要你记住的是，只有产生生效的那次扫描能做最后一道检查。**

### 3.5 读集跨拥有者时剩什么

一条 intent 的依赖可能横跨几个拥有者，比如 line.state 在单元控制器、recipe 在 MES。读集按拥有者拆成 $R_1, \ldots, R_k$，执行命令的那个控制器只能比对它拥有的那部分版本，其余部分仍然退回 $t_g$ 或 $t_c$ 时刻的副本检查，各自带着自己的区间。

按账本算，$k = 2$ 时要两次检查才够。能落在拥有者身上的只有 1 次，于是必然留 1 段区间。==一次扫描只关得掉自己拥有的那一段==。要把整段关掉得靠分布式事务，论文明确说不提供，所以保证只在子集上成立。

**这节要你记住的是，一个控制器只关得掉它拥有的那段区间。**

### 3.6 拒绝级联与 stop 的例外

放行的检查是一条级联，任何一步不过就停在那里，不往下走。

```
收到 intent
  schema 不合规 或 出现未知字段  -> 拒绝，后面都不做
  按 action_type 追加操作员强制谓词（生产者删不掉）
  action_type 属于 stop 类      -> 记审计，立即放行，不取锁，不写日志
  已过时间 > min(w, d) 或 P 或 S 不成立 -> Revoke
  d 已过而 w 未过                -> Expired
  目标忙                        -> Delay
  声明了降级策略                -> Degrade，换载荷后立即重验
  其余                          -> Authorized，同时记下 ν_R(t_v)
网关（乐观）读快照，比时间、P、S、ν_R(t_g) = ν_R(t_v)，任一不成立即 Withheld
网关（原子）请 XAIR 在一次 store 操作里比版本与时间，追加授权记录，失败即 Withheld
控制器扫描，版本仍等于命令携带的值（PLC 还要时间没过）才执行，否则拒绝
```

stop 这一类是刻意开的口子。fail-closed 适合增加活动的动作，重启、移动、抓取都算，用在 stop 上就把"停不下来"做成了安全缺陷。所以动作类型在策略里被分到 stop、start、motion、reset、shutdown、other 六类，类别不由生产者给，AIS 里没有这个字段，跟着动作类型走。stop 类的 intent 只要 schema 有效就放行，声明的谓词留着审计但不求值。已过时间和陈旧快照都撤不掉它，它也不在目标上取锁，同一批里优先于同目标的其他 intent。

stop 还顺带围栏在途的命令。它被授权时把自身时间写进上下文。其他 intent 都带一条谓词，要求这个时间不晚于自己的决策时刻。于是决策早于 stop 的 RESUME 不管在验证前还是验证后被提交，都会在自己的重检或提交处被判假。

这里的代价要说出来。stop 不进 actuation log，所以日志不是全部已放行命令的完整记录。另外这条围栏只管一个 XAIR 进程里的一个目标，stop 之后的放行它管不到。

**这节要你记住的是，拒绝要级联，但 stop 不能被任何一道拦住。**

## 四、结果

评测按五个问题铺开。RQ1 问加不加现场前置条件有什么差别。RQ2 问远端写者能改上下文之后该在哪读。RQ3 问每条放行路径各留下什么、最后一道检查该由谁做。RQ4 问版本条件在上下文频繁更新时的代价，以及生产日志里漂移的频率。RQ5 问运行时在边缘处理器上的开销、扩展性与故障表现。

口径先交代清楚。同一套 AIS 载荷和漂移时序在所有闸门下回放，闸门之间只差"在哪读、怎么比"，时间校验器与谓词求值器共用。所有实验取 $\varepsilon = 0$，即认为生产者与校验端的钟一致。依赖时序的实验以 campaign 为单位，分布式试验台跑五轮并给范围。作者把结果分成两类，符合性测试的结局由设计决定，零不算发现；测量类的结果才可能不一样。六个配置是单机、容器分布、保留核、广域节点、局域网节点、嵌入式板，另有 OpenPLC 运行时。

判据是成对的两个数。实验的地面真值在跑之前声明，$\mathcal{O}$ 是实验已在名义放行前失效的那批 intent，$\mathcal{V}$ 是在 $[t_v, t_m]$ 上一直有效的那批，历史违规的两批都不进。

$$ \mathrm{SER} = \frac{\sum_{I \in \mathcal{O}} Y(I)}{|\mathcal{O}|}, \qquad \mathrm{FPR} = \frac{\sum_{I \in \mathcal{V}} \big(1 - Y(I)\big)}{|\mathcal{V}|} \tag{5} $$

$Y(I) = 1$ 表示放行。一个 fail-closed 的闸门只能靠这两个数一起看，只看漏检会奖励拦得多的设计。

### 4.1 落点决定漏在哪一段

先看 store 那一侧。E3 把失效写入注入在验证之后 0 到 100 ms，每个偏移 30 次。排序在检查之前的写入全部被挡住，乐观与原子两种模式都一样。剩下的是检查到中间件调用之间那一段，分布式中位 1 到 2 ms，嵌入式板上约 4 ms。

撤销过的变化只有带版本的闸门拦得住。网关等待的时候把线暂停再恢复，检查那一刻谓词又全部成立。不带版本的闸门把这类 intent 全放出去（250/250），读集版本与谓词真值版本一条没放（0/250），两个物理节点上分别是 50/50 与 0/50。OPA 也照这条规律走，只判谓词时 250/250，拿到 XAIR 给的读集版本之后 0/250。保护来自版本，跟着版本走。

stop 是另一条路径。提交一个 RESUME，把它的重检或提交延后 40 ms，再在同目标上 0 到 60 ms 内放一个 stop，每种模式 330 次注入。没有围栏时 238/330 与 245/330 的 RESUME 在 stop 之后才放行。有围栏时两种模式都是 0/330，95% 上界 1.2%，每格 100 次合法对照试验照常放行。

| 放行路径 | 分布式 陈旧 | 分布式 历史违规 | 广域 陈旧 | 局域网 陈旧 | 局域网 历史违规 |
|---|---|---|---|---|---|

| 乐观 联锁 | 0/1100 | 285/1000 | 0/180 | 0/180 | 1/140 |
| 原子 联锁 | 0/1100 | 297/1000 | 0/180 | 0/180 | 3/140 |

要读的是第三列和第六列，两列都是历史违规。陈旧那几列里联锁和版本条件命令全是零，看不出差别，差别全在历史违规那一列。1100 次注入试验、每条路径、五轮 campaign，联锁与版本条件命令的 95% 上界都低于 0.35%（Wilson）。OpenPLC 上同样的格局，无条件命令约六分之一在暂停的线上生效，联锁与版本条件命令各 0/180，上界 2.1%。

### 4.2 版本作用域的代价

| 闸门 | 版本 | 合成更新 20 Hz | 合成更新 100 Hz | 液压记录 10 ms 间隔 |
|---|---|---|---|---|
| XAIR | 全局 | 12% | 64% | 未测 |
| XAIR | 读集 | 0 | 0 | 37% |
| XAIR | 谓词真值 | **0** | **0** | **0** |
| OPA | 无版本 | 0 | 0 | 0 |
| OPA | 读集 | 0 | 0 | 26% |

表里的百分数是合法 intent 被撤的比例，条件都在分布式试验台上，100 Hz 是背景写者改一个无关字段或用当前值重写 line.state，所以每一次撤都是误撤。读集与谓词真值在离散更新下都是零，液压那条记录把它们分开了。那段公开记录从不碰 line.state，可压力几乎每一条通知都在变。一条要求压力低于阈值的 intent，在新值从未越阈的情况下被撤掉 37%。==读集版本在离散状态上零误撤，到了连续信号上和全局版本一样糟==。

控制器那边同一个问题重演。给控制器三个快变量各按 20、50、100 Hz 变化，合起来每秒 60、150、300 次，而合法命令只读 line.state。

| 控制器版本的覆盖范围 | 20 Hz | 50 Hz | 100 Hz |
|---|---|---|---|
| 全部控制器状态 | 37% 未执行 | 92% 未执行 | 100% 未执行 |
| 只覆盖 line.state | **0/800** | **0/800** | **0/800** |

第一行是两级相加，网关自己先撤了 10%、25%、46%（镜像版本动了），控制器再拒了 30%、89%、100%。==控制器版本的覆盖范围比它的比较速度重要得多==。用只覆盖 line.state 的版本，三种速率下 800 条合法命令一条没被拒。历史违规那一侧，两种覆盖范围都没让一条过去，200 次暂停加恢复试验每格零。

### 4.3 边缘板上的开销

| 板子 | 顺序吞吐 | 端到端中位 | 全局版本误撤 20 / 100 Hz | 100 Hz 下的检查间隔 | 常驻内存 |
|---|---|---|---|---|---|
| Raspberry Pi 4 | 167 到 168 intents/s | 5.7 ms | 14% / 99% | 8.6 ms | 96 MB |
| VisionFive 2 | 148 到 152 intents/s | 6.4 ms | 26% / 95% | 9.9 ms | 93 MB |

这里要交代清楚 **148 到 168 intents/s** 是什么条件下测的。两块板各四核，XAIR 进程钉在一个核上，store、网关、负载生成器各占一个核，顺序提交。板子是 Raspberry Pi 4（Cortex-A72，实时内核）和 VisionFive 2（SiFive U74，RISC-V）。同一份单进程运行时在服务器保留核上是 909 到 956 intents/s，板上大约六分之一。

慢的闸门把 $\lambda \Delta_g$ 放大，所以全局版本在板上 100 Hz 下撤掉 95% 到 99%，比服务器上的 64% 更狠。读集版本与谓词真值版本在板上同样零误撤。

谓词注册表变大时还有另一笔账。store 的更新延迟在 10 个谓词时是 2.3 ms，1000 个时 16.5 ms，10000 个时 206 ms，这是文档布局的数字，哈希布局是 7.1 ms 与 93 ms。延迟越长，谓词翻转落进验证与检查之间那段的机会越少。1000 个谓词、100 Hz 的两种布局里，100 次翻转各有 87 与 91 次不再落进那段区间，10000 个谓词时一次都不落。这个规模下协议本身测不到撤销过的变化，滞后自己倒成了新的盲区。

### 4.4 生产日志里的漂移有多频繁

E6 用一份作业车间的生产日志。一分钟内发生的漂移不到 1% 的决策（0.13%，按空闲时长均匀取决策），可决策一旦挑在机器刚变空闲那一刻，一分钟内就有 14%。等一小时的决策，比例是 5.4% 到 43%，取决于调度怎么排，光换产品这一项最多到 2.2%，故障这一项 0.035% 到 0.059%。

把一个月日志压 4320 倍时间重放到分布式试验台，每种延迟取 2000 个决策、每个决策过五道闸门。30 个工厂分钟那一档有 35 个决策对所有闸门都已过期，240 分钟那一档有 147 个。直接放行全放了，XAIR 各版本一个没放，陈旧放行率的上界分别是 9.9% 与 2.5%。全局版本在这两档各撤掉 41/1963 与 39/1852 条合法决策，读集与谓词真值零。两档的更新流一样，2.81 Hz，所以全局版本的代价差不多。

公式 (4) 的准确度也报了。用实测闸门延迟代入，两种写法取较好的那个，在单机、分布式、液压记录、物理节点各格上差 3.5 到 6.7 个百分点，板上差 13 个点以内。板上把更新率那几格重做到 1200 次试验，12 个偏差里 10 个是低估，低估 3.5 到 12.6 个点，另外两个高估约 1 个点。作者说这个差多半来自版本读取到比较之间那一段没被 $\Delta_g$ 覆盖，没分离出来，所以公式当一阶指南用。

**这节要你记住的是，落点决定漏不漏，作用域决定撤不撤。**

## 五、局限

论文自己承认的部分逐条列在下面，强度照原文。

- 结果来自软件控制器的原型，不构成安全认证。XAIR 保证的是 intent 声明的与操作员强制的假设在放行时仍成立，这个性质比物理安全窄。
- 乐观模式的 $]t_g, t_m]$ 无人看守，原子提交不缩短这个区间。
- 线性化的授权只在一个 store 主上成立。读集跨几个拥有者时，保证只在控制器拥有的那个子集上成立，论文不提供分布式事务。
- A4 要求版本值不复用，而评测里的 PLC 程序每次运行从零起，16 位寄存器约 327 s 回绕，只在一个运行周期内满足。
- 谓词文法只支持合取。析取与有界时序算子原理上能加进来，原型没有。
- AIS 只能检查已声明的假设，管不了声明不完整。操作员策略补的是已知缺口，而策略接口本身要保护，原型只允许带操作员令牌的请求改策略。
- 不认证生产者，也不认证上下文写入者，不处理 store 的写授权。作者把这件事列为部署前提，论文引到 IEC 62443 的分区上，但原型没做。
- stop 不进 actuation log，所以日志不是全部已放行命令的完整记录。
- 评测层面的缺口有几条。注入的写入都没能落进 $]t_g, t_m]$，分布式试验台这一点上只量到区间宽度。控制器结果描述的是软件控制器的扫描边界，物理控制器与有线 I/O 的现场试验还没有。物理节点是消费级硬件走 VPN 与 Wi-Fi，不是产线网络或现场总线。E9-crash 的执行器是桩。store 滞后在谓词注册表变大时的陈旧放行率没测，只测了滞后本身。漂移率只来自一条生产日志。
- 时钟偏移 $\varepsilon$ 在实验里取零，物理节点上是事后对公共时间源测的，Apple 那台在 55 ms 以内，生产主机在 4 ms 以内，树莓派 4 在时间守护下是 33 µs。作者说这个量级只在新鲜度窗口接近传输延迟时才会改变判定。

下面是编者补充，论文未将其列为局限。

一处是板上并发没测。E7 报的 148 到 168 intents/s 是顺序提交，四核里另外三核被 store、网关、负载生成器占着。并发多生产者只在服务器保留核上跑过（最多 50 个生产者、关闭回路全部放行），板上那套数字说明装得下，不说明产线节拍下还有余量。

另一处是存量控制器的改造成本没算。论文把版本条件命令映射到 OPC UA 方法、IEC 61499 的功能块事件、PLCopen 运动块的执行输入上，这条路线在协议层面说得通。可老 PLC 的程序要改，参数区要腾出版本寄存器，改完还要过安全认证，这三件事的代价论文一句没提。

**这节要你记住的是，这些保证全挂着前提，前提破了就没有保证。**

## 六、我的评价

这一节是作者观点。

做得最对的是把问题从"快不快"挪到"看的是谁的状态"。论文里有一句证据很干净，==最快的闸门每次注入漂移都失败，最慢的那一个零失败==。那个从不刷新的缓存就是最快的现场闸门。延迟这个数字脱离一致性类别、观察边界、漂移协议就没有意义。

第二个做对的是地面真值先声明。评测最容易作弊的地方是让闸门自己定义什么叫过期，作者把失效集合在跑之前钉死，再用 SER 与 FPR 成对报，fail-closed 就没法靠拦得多拿分。

第三个是承认自己不新。If-Match、CAS、fencing token、使用控制、租约、乐观并发控制全被点名，贡献落在"哪里比、比哪个版本"上，这个定位比声称发明了机制要结实。

存疑的地方也有几处。

一个是版本作用域的账还没算成一笔总账。谓词真值版本误撤最低，但每次碰到被读路径的更新都要重求已注册的谓词，store 的更新吞吐在 1000 个谓词时按文档布局掉到 53 次/秒，按哈希布局也只在 100 Hz 下撑住。注册表涨到 10000 条时掉到 4.9 与 10.8 次/秒。这个规模下滞后本身成了新的盲区，作者自己说这部分没测。

一个是"所有写入都走 XAIR 的上下文接口"这条前提。==这条前提破了，每道闸门同时失明==。它写进了 Table 4，可现实里直连 HMI、旧 MES 接口、旁路脚本都能写状态，论文没有量化这类写入占多大比例。

一个是板上的数字容易被读成"能上产线"。单核顺序 148 到 168 intents/s，端到端中位 5.7 到 6.4 ms，跑得过很多监督动作。产线节拍里稀缺的是确定性的尾延迟，论文给的是中位与 99 分位扫描时间，端到端尾延迟没给。

它想往哪走写得挺具体，OPC UA 伴随规范里加版本与截止时间的入参，IEC 61499 里做成功能块，AAS 子模型路径直接当 AIS 的路径，信任边界按 IEC 62443 划。这些都是把机制变成接口的动作，方向对。

**这节要你记住的是，把落点和作用域拆开问，是这篇最立得住的地方。**

## 七、可以接着做什么

一，把版本条件命令做成 OPC UA 方法的标准入参，然后拿一台存量 PLC 实测改造后的扫描开销与认证成本。论文只说到协议能承载，没说改起来多贵。

二，读集跨拥有者时用 $k$ 段版本加一个轻量两阶段提交，测"分区保证"与"分布式事务"之间的代价差。论文里这一段是直接放弃的。

三，把作用域的选择自动化。读集能从谓词语法直接推出来，$\lambda$ 能从更新流估，公式 (4) 给了一个可算的误撤预期，于是三档版本可以按目标 FPR 选。这是把论文的机制做成配置项。

四，把决策时刻当成调度变量。既然漂移率由"决策在什么时候发生"主导，机器刚空闲那一刻做决策有 14% 会在一分钟内失效，那就让规划器尽量把决策挪近释放，而不是把窗口做大。

五，去真实产线上量"绕过上下文接口的写入"占多少比例，以及用数字孪生状态兜底时偏差怎么处理。这一条决定整套机制在存量车间里能用多大面积。

**这节要你记住的是，五条线索都从论文让出来的缺口里长出来。**

## 名词速查

| 术语 | 一句话解释 |
|---|---|
| 执行间隔 | 动作被提出时允许、被放行时已不允许的那段落差 |
| AIS | 动作意图契约，生产者随命令声明有效期与依赖的现场条件 |
| XAIR | 执行 AIS 的运行时，负责验证、授权、提交与审计 |
| intent | 一条带有效期与前提条件的动作请求 |
| 新鲜度窗口 w | 验证那一刻允许距决策多久 |
| 截止时间 d | 释放那一刻允许距决策多久，缺省等于 w |
| 前置条件 P | 生产者声明的软前提，通常是路径与字面量的比较 |
| 硬约束 S | 生产者声明的硬前提，同样不被认证 |
| 读集 R(I) | 谓词引用到的上下文路径集合 |
| 读集版本 ν_R | 读集上任一路径最近一次值变化对应的版本 |
| 谓词真值版本 π_I | 任一谓词注册或真值翻转对应的版本 |
| 全局版本 | 每一条被接受的更新都推进的版本 |
| 串行化域 | 一个组件按自己顺序处理更新的范围 |
| 副本 | 任何可能滞后于拥有者的状态拷贝 |
| 闸门 gate | 释放前做最后一次检查的那个组件 |
| 乐观模式 | 网关重读快照重检后直接释放 |
| 原子模式 | 在 store 的一次操作里提交授权再释放 |
| 提交后失效 | 提交之后、释放之前到达的更新，区间不缩短，但能被版本查出 |
| 围栏 | 用 stop 的时间当谓词，把决策早于它的在途命令判假 |
| 版本条件命令 | 控制器只在自报版本仍等于命令携带版本时执行 |
| 控制器本地联锁 | 在扫描里直接判谓词真值的检查 |
| 历史违规 A-B-A | 谓词中途假过一次又恢复，放行时看起来合规 |
| 陈旧放行率 SER | 已失效的 intent 中被放行的比例 |
| 误撤率 FPR | 合法 intent 中被撤掉的比例 |
| TOCTOU | 检查与使用之间状态被改掉造成的竞争 |
| 时钟偏移 ε | 生产者与校验端时钟差的上界 |
| actuation log | 只追加的授权与放行记录，可幂等重放 |
| fail-closed | 任何一步判断不了就按拒绝处理 |
| 扫描周期 | 控制器按固定周期执行一次程序的循环，评测里是 10 ms |
